# The Connection Agents (The Data Bus)

## Executive Summary
While the **Managing Agents** (C-Suite/VPs) govern divisional strategy and the **Worker Agents** execute specific tasks, the **Connection Agents** are the systemic nervous system of the organization. They do not generate product or marketing material; instead, they act as strict **API Gateways and Routers** between divisions.

In a GitHub Actions framework, these Connection Agents are the automated workflows (`action.yml` files) that listen for specific file commits, validate the data schema, and route the payload to the next Managing Agent in the pipeline. All scripts run on **Python 3.11 / Node.js 24**. All AI calls are made exclusively via **NVIDIA NIM or Google Gemini free-tier endpoints.**

They exist to prevent cross-divisional chaos, infinite LLM loops, and hallucinated handoffs.

---

## 1. The Strategy & Ingestion Router (The Ostrich)
**Path:** `[Data Sources] ➔ CDO ➔ CPO`
**Trigger:** `on: push: paths: ['market_data/*.csv', 'user_feedback/*.json']`

### Functionality:
This Connection Agent listens for raw market or user data entering the repository.
1. It wakes up the **CDO Managing Agent** to sanitize and structure the raw data.
2. It validates that the CDO's output matches the `Market_Insights_Schema.json`.
3. If valid, it commits the file to `/specs/insights/` and triggers a GitHub Issue tagging the **CPO Managing Agent** to begin writing the Product Requirements Document (PRD).

---

## 2. The Execution Splitter (The Fork)
**Path:** `CPO ➔ [CTO (Engineering) + CMO (Marketing)]`
**Trigger:** `on: push: paths: ['specs/prds/*.md', 'specs/prds/*.json']`

### Functionality:
This is the most critical Connection Agent. It ensures parallel execution without bottlenecks.
1. Listens for the CPO to commit a finalized `PRD` (which must contain strict Acceptance Criteria).
2. It automatically splits the workflow:
   - **Branch A (Technical):** Routes the PRD to the **CTO Managing Agent** to break down into markdown tickets committed to `/engineering/backlog/`.
   - **Branch B (Go-to-Market):** Routes the exact same PRD to the **CMO Managing Agent** to generate the `Creative_Brief.json` and seed the `/marketing/campaigns/` folder.
3. Enforces a "Wait State." It prevents deployment until *both* engineering code and marketing copy are marked as "Ready."

---

## 3. The Quality Governance Gatekeeper (The Firewall)
**Path:** `[CTO + CMO] ➔ VP QA ➔ COO`
**Trigger:** `on: pull_request: types: [opened, synchronize]`

### Functionality:
This Connection Agent acts as the ultimate CI/CD fail-safe. It intercepts all output generated by Worker Agents before it hits the `main` production branch.
1. When a PR is opened by an Engineering Worker (Code) or a Content Worker (Copy), this agent intercepts the PR.
2. It triggers the **VP QA Managing Agent** (and Legal if the PR touches `/marketing/` or `/legal/` folders).
3. **Execution:** The QA agent runs an LLM-as-a-judge script comparing the PR diff against the original PRD Acceptance Criteria.
4. If it fails, the Connection Agent automatically comments on the PR with the failure reasons and requests changes from the Worker Agent. If it passes, it auto-merges and signals the **COO Managing Agent** for deployment.

---

## 4. The Feedback Loop (The Ouroboros)
**Path:** `[Live Production] ➔ Customer Success (CRO) ➔ CDO`
**Trigger:** `on: schedule: - cron: '0 0 * * 0'` (Weekly)

### Functionality:
This Connection Agent ensures the company learns and adapts continuously.
1. Triggers every Sunday at midnight.
2. It gathers telemetry from the `Customer Success` Worker Agents (e.g., Zendesk tickets, NPS scores, bug reports).
3. Routes this telemetry back to the **CDO Managing Agent** to process into the next batch of `market_data`, effectively restarting the ingestion loop.

## Strict Data Constraints for Connection Agents
To prevent LLM hallucination during handoffs, Connection Agents enforce rigid Payload Contracts. If an agent outputs data that does not match the schema, the Connection Agent fails the build.

### Example Payload Contract (CPO to CTO):
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "PRD_Handoff",
  "type": "object",
  "properties": {
    "feature_name": { "type": "string" },
    "user_story": { "type": "string" },
    "acceptance_criteria": {
      "type": "array",
      "items": { "type": "string" }
    },
    "technical_constraints": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["feature_name", "user_story", "acceptance_criteria"]
}
```
